# 參考來源與收尾區塊規範 v1.1

> 🌐 [English](references-disclosure.en.md) | **繁體中文**

> **適用對象**：所有會產生或修改 n8n workflow 的 Skill、使用本 Skill Pack 的 AI Agent、整合工程師
> **核心約束**：交付 workflow 之後，告訴使用者「這次實際參考了哪些資料」，而且只能說實話；我們提供的建議與掃描結果都是建議與資訊，由使用者決定
> **收尾區塊（單一權威定義在第 4 章）**：固定順序 ① 參考來源 ② 建議事項 ③ 資安掃描結果；以 workflow 的 Layer 3 說明便條與相關節點 `notes` 為正式紀錄，對話只放簡短摘要
> **相關規格**：參考來源分類（第 3、5 章）、節點註解（第 7 章）、資安掃描（第 8 章）；建議事項的內容規則見 [`security-guardrails.md`](security-guardrails.md) 與 [`native-first.md`](native-first.md)

---

## 1. 目的與原則

本 Pack 的立場是：**Skill 只是「大腦」**，不是範本倉庫。這條立場推出五個原則，揭露規範就是把它們落實成固定動作：

1. **產出永遠是最新、正確的**：替使用者產生的 workflow，一律依「使用者環境目前可用的節點與參數」從頭建構，不沿用舊節點、不假設舊範本的參數仍然有效。
2. **參考資料是被消化的，不是被直接使用**：範本、統計、Skill 只提供做法與判斷依據，不原樣複製進產出。
3. **執行完成以後，要告訴使用者這次參考了哪些資料**：使用者有權知道 workflow 的設計依據從哪裡來，才能自行判斷要不要信、要不要追查原文。
4. **揭露本身不能成為新的錯誤來源**：寧可寫「無」，也不編造、不灌水（見第 5 章）。

`tigerai-example-finder` 在「挑範例」階段已經會註明參考範本；本規範把同樣的做法擴大到整個 Pack，並固定寫進 workflow 本身的註解（Layer 3 說明便條與節點 `notes`）。
5. **註解是正式紀錄**：參考來源、建議事項與掃描結果寫在 workflow 裡，才會跟著 workflow 被匯出、交接與版本控制；對話只放摘要，不是唯一的紀錄。

## 2. 適用時機

- **適用**：任何會產生或修改 workflow 的 Skill。**產生 Layer 3 說明便條時**把收尾區塊（第 4 章）寫進便條與相關節點 `notes`，**交付結果時**在對話附上摘要。
- **目前接上的 Skill**：`sticky-note-to-workflow`、`tigerai-qa-mode`（交棒給前者時一併交出紀錄）、`code-to-workflow`、`tigerai-enterprise-patterns`、`tigerai-example-finder`、`n8n-code-to-native`、`code2n8n-pipeline`（管線最後一個階段）、`n8n-security-governance`（產生時建議的來源，內容規則在 [`security-guardrails.md`](security-guardrails.md)）。其他會產生或修改 workflow 的 Skill 比照辦理。
- **不適用**：只讀取、不產生也不修改 workflow 的動作（例如列出 workflow、查詢執行紀錄）。
- **邊做邊記**：AI 在工作過程中維護一份內部的「參考紀錄」，每讀一份會影響設計的資料，就記下「類別、出處、影響了什麼」。便條的「參考來源」區塊與對話摘要都從這份紀錄產生，兩處內容要一致；若便條寫完後又多參考了資料，要回頭補進便條，不偽裝成一開始就用了。
- **修改既有 workflow**：更新既有 Layer 3 便條時，把「參考來源」區塊改成「本次修改」所參考的資料，並保留先前的條目；「建議事項」與「資安掃描結果」區塊依修改後的最終 JSON 重寫；不要整段重寫成看起來只參考過一次。

## 3. 揭露內容的分類

共六類。**每一類都要出現**；沒有就明寫「無」，不可省略該行。

### ① 本機範例

- **內容**：本 Pack 內的 `cookbook/xx`、`examples/xx`。
- **格式**：`- 本機範例：<路徑>（<採用了什麼>）`
- **範例**：`- 本機範例：cookbook/01-webhook-to-slack.md（採用 webhook + set + 通知的三段骨架）`
- **沒有**：`- 本機範例：無`

### ② 統計與骨架知識

- **內容**：`research/` 底下的文件，要寫到章節。
- **格式**：`- 骨架與統計知識：research/<檔名> §<章節> <主題>`，多筆以頓號或分行列出。
- **範例**：`- 骨架與統計知識：依 research/patterns.md §2.3 排程觸發骨架（schedule）、§3 反模式 2（缺錯誤處理）`
- **沒有**：`- 骨架與統計知識：無`
- **注意**：只在 `research/patterns.md` 看到某範本被列為「代表範本」，不代表讀過該範本；那只算 ②，**不可**升格寫成 ③。

### ③ n8n.io 官方公開範本

- **內容**：從 n8n.io 即時查閱過的官方公開範本。**只有使用者同意查詢過才會有這一類。**
- **格式**：`- n8n.io 官方範本：#<編號>《<標題>》 https://n8n.io/workflows/<編號>`，後面接「只參考做法，已用目前版本節點重新建構」。
- **範例**：`- n8n.io 官方範本：#<ID>《<標題>》 https://n8n.io/workflows/<ID>（只參考做法，已用目前版本節點重新建構）`
- **沒有（未查詢）**：`- n8n.io 官方範本：無`
- **使用者拒絕**：`- n8n.io 官方範本：使用者選擇不查詢外部範本`
- **編號與標題**：照實抄自查閱到的頁面；若範本在 `research/patterns.md` 內有列出，編號與標題要與該檔一致。本規範的範例若無實際查閱，一律用 `#<ID>` 佔位並標明示意。

### ④ 原廠 Skill 與社群 Skill

- **內容**：實際打開讀過、並影響設計的 `skills/_vendor/` 內的 Skill（原廠與社群）。
- **格式**：`- 原廠／社群 Skill：<Skill 名稱>（<上游名稱>，<釘選版本>）`
- **版本怎麼取**：**依 `skills/_vendor/upstream-pins.json`**，讀到什麼寫什麼。
  - 該上游有釘選版本：寫其釘選的版本標記（必要時附 commit 前 7 碼）。
  - 該上游沒有釘選版本：寫「未釘選」，不要自行推測或寫成最新版。
  - 欄位名稱與內容以讀取當下的檔案為準，**規格不寫死任何版本數字**。
- **範例**：`- 原廠／社群 Skill：n8n-expression-syntax（czlonkowski/n8n-skills，<依 upstream-pins.json>）`
- **沒有**：`- 原廠／社群 Skill：無`
- **注意**：Pack 自己的 Skill 與 `spec/` 規格（例如 `sticky-note-to-workflow`、三層結構規範）屬於「Pack 內建規格」，每次都會用到，不逐一列出。

### ⑤ 目標 n8n 版本

- **內容**：這次依哪一版 n8n 的節點與參數建構。
- **格式**：`- 目標 n8n 版本：<版本或範圍>（依 <來源>）`
- **取值順序**：
  1. 使用者的實例版本（使用者告知，或經 `n8n-api-bridge` 讀得）：寫該版本。
  2. 使用者未提供：寫「未指定」，並註明改依 `docs/n8n-version-compat.md` 的實測版本範圍（寫讀到的範圍，不寫死在規格裡）。
  3. 使用者的版本在實測範圍之外：照實寫「超出 Pack 實測範圍，未實測」。
- **範例**：`- 目標 n8n 版本：<x.y.z>（使用者提供；Pack 實測範圍見 docs/n8n-version-compat.md）`
- **沒有**：這一類不能寫「無」，至少要寫「未指定」並說明依據。

### ⑥ 沒有參考外部範本時的標準句

當 ① 與 ③ 都是「無」時，這兩類可合併成下面這一句（②④⑤ 仍照常列出）：

> 沒有參考外部範本，依需求與 Pack 內建規格設計

- **禁止編造來源**：沒有就是沒有，不為了顯得有根據而補一個。
- **禁止列出沒實際用到的資料**：沒讀過、或讀了但沒影響設計的，不列。

## 4. 收尾區塊的統一定義（權威）

本章是整個 Pack 唯一的收尾定義。[`security-guardrails.md`](security-guardrails.md)、[`native-first.md`](native-first.md)、[`sticky-note-three-layer.md`](sticky-note-three-layer.md) 與各個 Skill 只引用本章，不各自重述順序或格式。

**總原則：我們提供的建議、參考來源與掃描結果，都寫在 workflow 本身的註解裡，註解就是正式紀錄；對話只放簡短摘要並指向註解。** 所有資安與原生節點優先的內容都是**建議**：AI 提出、說明理由，由使用者決定要不要採用，不因使用者不採用而拒絕或阻擋。

### 4.1 三個區塊與固定順序

| 順序 | 區塊 | 內容 | 內容規則在哪 |
|---|---|---|---|
| ① | 參考來源 | 這次實際參考了哪些資料 | 第 3、5 章 |
| ② | 建議事項 | 資安建議（`security-guardrails`）、原生節點優先與 Code 節點說明（`native-first`），含使用者選擇不採用的項目 | 4.3 節；規則編號見 [`security-guardrails.md`](security-guardrails.md) 第 2 章與 [`native-first.md`](native-first.md) 第 7 章 |
| ③ | 資安掃描結果 | 規則式掃描的結果 | 第 8 章 |

順序固定為 ① → ② → ③，三個區塊連續呈現，不另起第二個收尾。

### 4.2 三處位置

| 位置 | 放什麼 | 角色 |
|---|---|---|
| Layer 3 說明便條（`color = 5`，`position.y` 在 600–900） | ①②③ 三個區塊的完整內容 | **正式紀錄** |
| 相關節點的 `notes` | 只針對該節點的建議，簡短一行（4.4 節） | 正式紀錄（節點層級） |
| 對話收尾 | 3–5 行摘要，並指向上面兩處註解（4.5 節） | 摘要，不是正式紀錄 |

- 同一個 workflow 有多張 Layer 3 便條時，三個區塊放在最左邊那張，緊接在標題之後（與 `cookbook/_runnable-Q2-order-line.json` 的「範例查詢結果」同位置、同風格）。這是對 [`sticky-note-three-layer.md`](sticky-note-three-layer.md) §4.2 模板的補充，不取代其他各段。
- 對話摘要與註解若不一致，以註解為準；對話中提到的內容，註解裡都要找得到。

### 4.3 Layer 3 便條的模板

```markdown
**參考來源**
- 本機範例：<cookbook/xx 或 examples/xx（採用了什麼）／無>
- 骨架與統計知識：<research/xx §n.n 主題／無>
- n8n.io 官方範本：<#編號《標題》網址／無／使用者選擇不查詢外部範本>
- 原廠／社群 Skill：<名稱（上游，版本）／無>
- 目標 n8n 版本：<版本，依據>
- 參考方式：只參考做法，已用目前版本節點重新建構

**建議事項**
- `<規則編號>`：<狀態>（<一句話說明，可省略>）
- ……每條建議一行……
- 不適用：`<規則編號>`、`<規則編號>`
- 以上皆為建議，最終決定在使用者；建議不等於安全

**資安掃描結果**
- <見第 8.3 節的格式>
```

沒有參考外部範本時，「參考來源」改成：

```markdown
**參考來源**
- 沒有參考外部範本，依需求與 Pack 內建規格設計
- 骨架與統計知識：<research/xx §n.n 主題／無>
- 原廠／社群 Skill：<名稱（上游，版本）／無>
- 目標 n8n 版本：<版本，依據>
```

**「建議事項」區塊的規則**

1. **每條建議一行**，開頭是規則編號，後接狀態與選填的一句話說明。規則編號沿用 [`security-guardrails.md`](security-guardrails.md) 第 2 章的 13 個編號，以及 [`native-first.md`](native-first.md) 的 `native-first:code-node`。
2. **狀態只有四種**：

   | 狀態 | 意思 | 說明欄寫什麼 |
   |---|---|---|
   | 已採用 | 建議適用，已照做 | 做法（一句話）；掃描只涵蓋局部的，註明人工要確認的部分 |
   | 使用者選擇不採用 | 使用者知道建議與風險，選擇別的做法 | 使用者選了什麼（一句話）。**不需要附理由**；使用者願意說明時才寫 |
   | 不適用 | 這個 workflow 沒有觸發情境 | 可省略；合併成最後一行列出編號即可 |
   | 尚未能自動檢查 | 建議適用，但掃描器沒有對應規則，只有 AI 自查 | 已做了什麼，以及請人工確認的地方 |

3. **不確定時，不要選「已採用」**，選「尚未能自動檢查」並寫明哪裡不確定。
4. **「不適用」的規則編號合併成一行**列出（例如 `不適用：form:no-auth、exec:ssh`），不必逐條各占一行；其他三種狀態一條一行。
5. **Code 節點說明**用 `native-first:code-node` 這一條。沒用 Code 節點：`native-first:code-node`：已採用（未使用 Code 節點）。用了：`native-first:code-node`：已採用（Code 節點：N 個／全部節點 M 個），下面每個 Code 節點縮排一行「節點名稱：理由」。N 與 M 的算法見 [`native-first.md`](native-first.md) 第 7 章。理由與該節點 notes 寫的一致。使用者明確要求在可由原生節點完成的地方使用 Code 時，狀態寫「使用者選擇不採用」。
6. **無建議時寫「建議事項：無」**：這個 workflow 沒有任何建議需要提出（所有項目都不適用）時，整個區塊寫成一行 `建議事項：無`。不要省略區塊，也不要為了讓區塊看起來充實而編造建議。
7. **內容與最終的 workflow JSON 一致**：寫「已採用」的項目，JSON 裡找得到對應設定；修改 workflow 之後，這個區塊也要跟著更新。

**JSON 範例**（便條節點；內容為示意，沒有參考外部範本）：

```json
{
  "id": "sticky-ai-1",
  "name": "AI 實作說明",
  "type": "n8n-nodes-base.stickyNote",
  "typeVersion": 1,
  "position": [0, 700],
  "parameters": {
    "color": 5,
    "width": 560,
    "height": 520,
    "content": "### 🤖 AI 實作說明\n\n**參考來源**\n- 沒有參考外部範本，依需求與 Pack 內建規格設計\n- 骨架與統計知識：research/patterns.md §2.2 webhook-fire\n- 原廠／社群 Skill：無\n- 目標 n8n 版本：未指定（依 docs/n8n-version-compat.md 的實測範圍）\n\n**建議事項**\n- `secret:hardcoded`：已採用（憑證由 n8n 憑證機制引用）\n- `webhook:no-auth`：使用者選擇不採用（僅供內網健康檢查）\n- `error:no-handling`：尚未能自動檢查（已接 Error Workflow，請人工確認通知對象）\n- `native-first:code-node`：已採用（未使用 Code 節點）\n- 不適用：form:no-auth、exec:ssh\n- 以上皆為建議，最終決定在使用者；建議不等於安全\n\n**資安掃描結果**\n- 規則式掃描（不代表沒有其他風險）：0 項命中，1 項已知悉\n  - `webhook:no-auth` @ Health check（已知悉）\n\n**節點選型**\n- `webhook`：對應 @trigger"
  }
}
```

### 4.4 節點 notes 裡的建議

針對**特定節點**的建議，寫在該節點的 `notes`，簡短一行，規則編號沿用 4.3 節的編號：

```text
建議 <規則編號>：<一句話>（<狀態>）
```

例如：

- Webhook：`建議 webhook:no-auth：建議加 Header 認證（使用者選擇不採用）`
- Code 節點：`為什麼用 Code：已評估 Edit Fields，<具體原因>`（這是 `native-first:code-node` 的 notes 寫法，細節見 [`native-first.md`](native-first.md) 第 5 章）
- AI Agent：`建議 ai:agent-no-guardrails：輸入與輸出建議過原生 Guardrails 節點（尚未能自動檢查）`

規則：

1. 只在該建議**影響這個節點**，而且需要提醒時才寫：使用者選擇不採用、尚未能自動檢查而需要人工確認、採用了非顯而易見的做法。已採用而且一看就懂的設定可省略（完整狀態仍在 Layer 3 便條）。
2. 屬於整個 workflow 的建議（例如 `error:no-handling`、`data:pii-minimization`）只寫在 Layer 3 便條；使用者要留已知悉行時，寫在觸發節點的 notes。
3. 使用者同意的話，可以另起一行 `guardrail-ack: <規則編號>`，掃描器讀得到（細節見 [`security-guardrails.md`](security-guardrails.md) 第 3 章）。這一行是選用的。
4. 與第 7 章一致：一到三句為限，寫「為什麼」，不重複節點上已經看得出來的資訊。

### 4.5 對話摘要

交付那則回覆的最後，附 3–5 行摘要，並指向註解。對非技術使用者（例如問答模式）用白話，不出現 DSL、Layer、webhook 等術語。

```markdown
**交付摘要**
- 參考來源：<一句話，例如「沒有參考外部範本，依需求與內建規格設計」>
- 建議事項：<例如「5 項建議，已採用 3、你選擇不採用 1、尚未能自動檢查 1」，或「建議事項：無」>
- 資安掃描：<例如「規則式掃描發現 1 項提醒」，或「未發現規則命中」，或「未執行，原因……」>
- 完整內容寫在 workflow 的「AI 實作說明」便條與相關節點的備註裡，以註解為準。
```

摘要裡的數字與註解必須對得上，而且不重新貼出註解的內容。

### 4.6 便條與 notes 的精簡規則

1. **每條建議一行**，不寫長段落；較長的說明另放 Layer 3 的「已知限制」。
2. **AI 不會把真實機密、疑似金鑰原文、內網位址或真實資料寫進便條或 notes。** 範例與說明用佔位字或明顯的假值。
3. **掃描命中只寫規則名稱與節點名稱**，不貼掃描輸出的樣本欄位。
4. **寫成合法 JSON 字串**：便條內容放在 `parameters.content`，節點 notes 放在 `notes`，都是單一 JSON 字串，所以：
   - 換行一律寫成 `\n`，不可有真正的換行字元或 Tab。
   - 內容中的雙引號寫成 `\"`；反斜線寫成 `\\`。範本標題常含雙引號、引號或表情符號，寫入前先處理。
   - 表情符號與繁體中文可直接寫入（UTF-8），不必轉成 `\u` 序列。
5. 便條高度（`height`）隨行數增加，避免新增的段落被截掉；位置仍須維持在 Layer 3 的 `y` 範圍內。
6. 寫完之後，對最終那一份 JSON 重新掃描（第 8.1 節）；掃描結果以最後一次為準。

## 5. 誠實規則

1. **只列實際讀過、而且實際影響設計的資料。** 讀了但沒影響設計的不列；沒讀過的不列。
2. **範本是被「消化」，不是被複製。** 凡列出範本（③，或 ① 中採用其骨架的範例），都必須寫明「只參考做法，已用目前版本節點重新建構」。若範本用了棄用節點，另外寫明「範本用 <舊節點>，改用 <目前節點>」。
3. **使用者拒絕查 n8n.io，就照實寫。** ③ 寫「使用者選擇不查詢外部範本」，不因此改寫成「無」，也不偷偷查。
4. **沒有就寫沒有。** 沒有外部範本時用 ⑥ 的標準句，不補一個看起來合理的來源。
5. **不誇大、不升格。** 只在統計文件看到的範本編號屬於 ②；沒有讀過內容就不能列為 ③。
6. **不冒充實測。** 目標版本若不在 `docs/n8n-version-compat.md` 的實測範圍內，要說「未實測」；不用任何暗示品質保證或可直接上線的字眼來包裝參考來源。
7. **AI 不會把機密與內網資訊寫進註解。** 參考來源只列公開出處與 Pack 內路徑；使用者的私有路徑、內網位址、憑證值，AI 都不會寫進便條或節點 `notes`。
8. **建議事項與掃描結果同樣如實。** 沒檢查的寫「尚未能自動檢查」，使用者選擇不採用的照實列出，沒有建議就寫「建議事項：無」（第 4.3 節）；不編造建議，也不靜默省略。

## 6. 反例與正例

### 反例 1：把「在統計文件看到」寫成「查閱過範本」

使用者沒有同意查詢 n8n.io；AI 只讀了 `research/patterns.md`，卻在便條的「參考來源」寫：

```markdown
- n8n.io 官方範本：#1961《Slack chatbot powered by AI》 https://n8n.io/workflows/1961
```

**錯在哪**：該範本只是 `patterns.md` §2.2 的代表範本清單，AI 沒有讀過內容，也沒有取得使用者同意查詢。**改正**：③ 寫「無」，② 寫 `research/patterns.md §2.2 webhook-fire`。

### 反例 2：灌水湊數

AI 只打開了一份 `n8n-expression-syntax`，卻列出十個 Skill 名稱與整個 `cookbook/`，「看起來參考得很完整」。

**錯在哪**：列出沒實際用到的資料，會讓使用者以為設計經過更多把關，是對依據的誤導。**改正**：只列實際讀過、影響設計的那一份，其餘不列。

### 正例 1：完全沒有外部參考

使用者描述簡單的「webhook 收單、組訊息、推通知」，AI 只依 Pack 內建規格與骨架知識建構：

便條的「參考來源」區塊：

```markdown
**參考來源**
- 沒有參考外部範本，依需求與 Pack 內建規格設計
- 骨架與統計知識：research/patterns.md §2.2 webhook-fire
- 原廠／社群 Skill：無
- 目標 n8n 版本：未指定（依 docs/n8n-version-compat.md 的實測範圍）
```

對話摘要的參考來源那一行：「沒有參考外部範本，依需求與內建規格設計」。

### 正例 2：多種來源，並記下改寫

使用者同意查詢 n8n.io；AI 參考了一個範本，範本用了舊的 Function 節點：

便條的「參考來源」區塊：

```markdown
**參考來源**
- 本機範例：cookbook/02-schedule-report.md（採用排程取資料、整形、寄送的三段骨架）
- 骨架與統計知識：research/patterns.md §2.3 排程觸發骨架（schedule）、§3 反模式 1（棄用節點）
- n8n.io 官方範本：#<ID>《<標題>》 https://n8n.io/workflows/<ID>（示意；範本用 Function 節點，已改用 Code 節點）
- 原廠／社群 Skill：n8n-expression-syntax（czlonkowski/n8n-skills，<依 upstream-pins.json>）
- 目標 n8n 版本：<x.y.z>（使用者提供）
- 參考方式：只參考做法，已用目前版本節點重新建構
```

## 7. 節點層級註解（notes）

揭露參考來源之外，節點本身的 `notes` 欄位也要有一致的寫法。這一章與 n8n 官方 Skill 的建議對齊，不另立一套。

### 7.1 規則

1. **只在「非顯而易見的設定」寫節點 notes。** 例如為了繞開某個限制而採用的變通做法、為什麼選這個節點而不是另一個、這個設定參考了哪個來源。
2. **內容寫「為什麼」，不重複「是什麼」。** 節點名稱與參數已經看得出來的事情，不必再寫一遍。
3. **顯而易見的節點不寫。** 例如名稱已說明用途的 Webhook、單純的欄位對映 Set，留空即可。
4. **多行運算式與 Code 節點要縮排並加註解**，讓不寫程式的接手者也能讀懂意圖。
5. **保持簡短。** 一到三句為限；較長的說明放進 Layer 3 說明便條或 workflow 的描述欄位。
6. **與參考來源的關係。** 如果某個設定直接來自某份參考資料，notes 可以簡短指出（例如「骨架參考 cookbook/01」）；完整清單仍以第 4 章 Layer 3 便條的「參考來源」區塊為準，notes 不取代它。
7. **針對該節點的建議也寫在這裡。** 資安建議與原生節點優先的說明（例如 Webhook 的認證、Code 節點評估過哪個原生節點、Agent 的 Guardrails）若影響這個節點，就寫成簡短一行；寫法見第 4.4 節。這類建議行是建議，不是檢查項目。

### 7.2 與官方做法的關係

n8n 官方 Skill（`n8n-workflow-lifecycle-official` 的「Readability」段落與其 `references/STICKY_NOTES.md`，以及 `n8n-expressions-official`）本來就有同方向的建議：節點 notes 留給非顯而易見的設定、說明「為什麼」而不是註解每個節點；便條用來標註而不是用來分組；多行運算式要縮排並加註解。本 Pack 在這些原則上與官方一致。

我們多做的是三件事：

- **便條規格化**：Layer 1 / 2 / 3 的位置、顏色與必含段落都有固定規格（見 [`sticky-note-three-layer.md`](sticky-note-three-layer.md)）。官方的建議是節點很少時不放便條；本 Pack 仍要求每個 workflow 至少有一張 Layer 3 便條，因為它還要承載憑證清單、前提假設、已知限制與參考來源。
- **便條可作為需求輸入**：使用者寫的 Layer 1 便條是可被解析的需求規格，不只是給人看的註解。
- **完成後把參考來源、建議事項與掃描結果寫進註解**：本規範的第 3 至第 5 章與第 8 章，統一定義在第 4 章。

### 7.3 統計佐證

在本 Pack 彙整的 13,947 個 n8n.io 公開範本中，93.1% 有便條，但只有約 10.1% 的範本在節點上寫了 notes；以節點計，帶 notes 的節點僅占 3.3%。也就是說，社群範本普遍會放便條，卻很少說明單一節點「為什麼這樣設定」。這是描述性統計，不是品質認證；它只用來說明這項建議補的是哪個缺口。（數字出處：[`../research/node-frequency.md`](../research/node-frequency.md) 的 §9.6「註解與說明」。）

### 7.4 與三層規範的關係

`sticky-note-three-layer.md` §3.1 已與本章統一：節點 `notes` 只在非顯而易見的設定才寫，說明「為什麼」；原本由逐節點 `notes` 承擔的「對應 Layer 1 哪個 `@step`」追溯，改由 Layer 3 便條的「節點選型」與「對應使用者需求」段承擔（該段逐條列出每個 `@trigger` / `@step` / `@on-error` 由哪個節點實作）。Layer 3 便條 §4.2 模板已納入本規範第 4 章的三個區塊；針對特定節點的建議行寫在該節點 `notes`（第 4.4 節）。

## 8. 資安掃描結果

每次產生或修改 workflow 之後，收尾區塊的第三項（③）是**資安掃描結果**。掃描結果是**資訊與建議**：AI 如實告訴使用者、說明每一項代表什麼風險、提出建議的處理方式，**由使用者決定要不要處理**。Skill 不因為掃描有命中而拒絕交付。

### 8.1 怎麼掃

- **時機**：交付前，對**實際要交付的 workflow JSON** 掃描。若 workflow 只存在於對話中，先存成暫存檔再掃。之後只要又改了 JSON（包含把掃描結果寫進便條），就對最終那一份重掃，結果以最後一次為準。
- **指令**（在 Pack 根目錄執行）：

  ```bash
  node scripts/security-scan.mjs <workflow.json>
  ```

  可一次傳多個檔案，也可用 `--glob`；`--format json` 可輸出機器可讀的結果。`--strict` 是掃描器選用的旗標（把 warning 也算入退出碼），**Skill 流程不使用，也不要求使用**。
- **性質**：這是**規則式掃描**（比對機密樣式、Code 節點的惡意樣式、明文密碼欄位、Webhook 沒設認證、非本機的 `http://` 位址），**不是 AI 審計**。深度審查仍靠 `n8n-security-governance` Skill 與人工。
- **涵蓋範圍的限制**：Code 節點只掃 `jsCode` 與 `functionCode` 欄位，不掃 Python 程式碼；規則是樣式比對，沒命中不代表沒有其他風險。

### 8.2 怎麼解讀結果（與腳本實際行為一致）

掃描器的規則分兩類：

- **護欄類**（對應 [`security-guardrails.md`](security-guardrails.md) 的建議，例如 `webhook:no-auth`）：一律是 warning，是建議，預設執行不會因為它們失敗。節點 notes 若有 `guardrail-ack: <規則編號>`，表示使用者已知悉，掃描器輸出 `ACK` 行，不計入 warning。
- **偵測類**（`secret:*`、`jscode:*`、`credential:plaintext` 等）：是 error，供 Pack 自己的 CI 檢查 repo 內的檔案。`guardrail-ack:` 對它們無效。

| 退出碼 | 意義 |
|---|---|
| `0` | 沒有偵測類 error。**可能仍有 warning 或 ACK**，所以不能只看退出碼，要看輸出：每個檔案沒有任何命中也沒有 ACK 時，才會印出 `OK <檔名>` |
| `1` | 至少一項偵測類 error；檔案讀不到或不是合法 JSON 也會以 error 計，同樣回傳 1。這是**資訊**，不代表不能交付 |
| `2` | 沒有指定任何檔案，或 `--glob` 沒有符合的檔案，實際上沒有掃到任何東西，要視為**未執行** |

- **error 與 warning 一視同仁地告知**：如實告訴使用者命中的規則名稱與節點名稱，說明風險，提出建議的處理方式。使用者決定處理的，修改後對最終那一份重掃；使用者決定不處理的，照實記下，不隱瞞也不替使用者決定。
- **偵測類 error 也只是告知與建議**：例如疑似機密外洩樣式、惡意程式碼樣式，AI 會提醒使用者並建議處理（例如把機密改走憑證機制、確認 Code 節點的來源），Skill 不因此拒絕交付。
- **ACK 行**：照實寫成「已知悉」，不當成修好，也不再重複提醒同一項。
- 輸出的樣本欄位可能含疑似機密的原文，或內網網址（例如 `secret:*`、`network:http-cleartext`）。**揭露時只寫規則名稱與節點名稱，不貼出樣本原文**（4.6 節）。

### 8.3 揭露格式

寫在 Layer 3 便條的「**資安掃描結果**」區塊（收尾區塊的第三項，位於「建議事項」之後）；對話只放一行摘要（4.5 節）。

沒有任何命中（輸出是 `OK`）：

```markdown
**資安掃描結果**
- 規則式掃描：未發現規則命中（不代表沒有其他風險）
```

有命中或有已知悉項目：

```markdown
**資安掃描結果**
- 規則式掃描（不代表沒有其他風險）：<N> 項命中，<K> 項已知悉
  - <規則名稱> @ <節點名稱>（<error／warning>）：<建議做法，或使用者的決定>
  - <規則名稱> @ <節點名稱>（已知悉）
```

無法執行（例如沒有 Node.js 環境、腳本不存在、退出碼為 2）：

```markdown
**資安掃描結果**
- 未執行資安掃描：<原因>
```

- **不省略不提，也不假稱通過。** 沒掃就寫「未執行資安掃描」；掃了但有命中，就不能寫成「未發現規則命中」。
- **對話摘要**用白話，對非技術使用者可把規則名稱換成一句說明（例如「Webhook 沒有設認證」）；完整的規則名稱與節點名稱以便條為準。
- 便條寫成合法 JSON 字串，規則同 4.6 節。

### 8.4 Code 節點說明的位置

Code 節點的說明（N 個／全部 M 個，與逐項理由，或「未使用 Code 節點」）屬於**建議事項**，不再另設一個收尾項目：寫在 4.3 節的 `native-first:code-node` 那一條，每個 Code 節點的理由也寫在該節點的 `notes`（4.4 節）。格式與計數規則見 [`native-first.md`](native-first.md) 第 5–7 章。以最終的 workflow JSON 為準，不省略、不低報。
