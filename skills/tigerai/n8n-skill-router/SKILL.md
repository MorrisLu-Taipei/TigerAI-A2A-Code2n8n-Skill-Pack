# n8n Skill 路由

繁體中文 | [English](SKILL.en.md)

呼叫 n8n 工具前，先確認使用者授權的動作與目標環境。執行環境的權限與範圍限制一律優先。

1. 讀[流程索引](references/pipeline.json)，選擇 `diagnose`（除錯）、`build`（新建）、`modify`（修改）、`convert`（程式轉換）、`review`（審查）或 `publish`（發布）。「打不通」先走唯讀除錯；新建、修改和轉換預設只產出草稿，不會自動進入發布。
2. 依路線的階段順序，載入路線的 `skills`、與任務相符的 `signals`，以及環境實際支援的 `adapters`。有 `choose` 時只選一個。首次連線前讀對應 adapter；不需連線則跳過。訊號對應的 Skill 若不在路線的階段內，只在排查相關問題時補讀，不增加階段或權限。階段內依索引排序，已載入的不用重讀。走 REST 時參考 `n8n-api-bridge`，只使用目標版本支援的操作。必要 Skill、工具或檢查無法取得，或不符合路線及階段的 `exit`，先停在該關；路線若另定 `exit`，以它為該路線的完成條件。
3. 遠端寫入或會有副作用的測試前，核對實例、工作流、動作及版本的授權。既有流程須先讀回草稿與發布基準，並依核准方式留存去敏備份。憑證用節點頂層的引用，與 `parameters` 同層；不得把秘密值寫入流程或日誌。已貼進對話的金鑰視為已暴露，請持有人輪替。
4. 發布另行核准。R1／R2 必須對到相同候選產物及目標，授權也要對到同一動作與版本。儲存庫的離線發布前檢查只比對證據，不驗證核可人的真實身分，也不授予寫入權限。走受控部署管道；不能把核可綁到實際要發布的版本，就停止。發布後讀回實際發布版；存草稿不是發布。無法讀回就標「尚未驗證」，實際觸發測試需要另行授權。

交接記錄現階段、下一步、已用的 Skill、證據位置和阻擋原因。Layer 3 便條是進度，不是核准證明。不要只為了留便條就寫回已上線的工作流。
