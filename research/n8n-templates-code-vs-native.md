# 社群範本裡的 Code 節點：用途分布與可由原生節點取代的估計

> [English](n8n-templates-code-vs-native.en.md) | 繁體中文

> **樣本**：13,947 個 n8n.io 公開範本（取得方式與完整性見 [`n8n-templates-method.md`](n8n-templates-method.md)；整份節點統計見 [`node-frequency.md`](node-frequency.md)）。
> **性質**：以下全是描述性統計與啟發式估計，不是對範本作者的批評，也不代表 Code 節點一定不好。本 repo 只收彙整數字，不收任何範本內容、編號、作者或程式碼片段。
> **目的**：給「AI 產生 workflow 時預設用原生節點」這項規格（[`../spec/native-first.md`](../spec/native-first.md)）一個實證背景：社群範本裡的 Code 節點到底在做什麼，有多少其實有原生節點可用。

## 2. 讀法與限制

1. **主類別是啟發式判斷。** 用程式碼文字的樣式（正規式）與複雜度（行數、分支、迴圈、函式數）判斷「這個節點主要在做什麼」，每個節點只取一個主類別，另記錄所有命中的次要類別。沒有執行程式碼，也沒有看上下游節點，所以會誤判。
2. **「可取代」不等於「應該取代」。** 估計的是「在不考慮可讀性取捨、也不考慮使用者環境版本的前提下，這段工作有原生節點或運算式可以做」。把簡單邏輯拆成十幾個節點未必更好懂（見 [`../spec/native-first.md`](../spec/native-first.md) §9）。
3. **看不到上游節點與原作者的理由。** 範本寫成 Code，可能是當時沒有對應的原生節點（Summarize、Remove Duplicates、Compare Datasets 等較晚出現）、可能是為了示範、也可能真的需要。
4. **行數** 指去掉空白行與整行註解後的行數；程式碼比對只看每個節點前 20,000 個字元（極少數壓縮過的長程式碼除外，不影響分類）。
5. **人工校驗是讀程式碼片段後的主觀判斷**（只看每個節點開頭的 280 至 420 個字元），邊界案例本來就模糊，見 §7。
6. **範本偏新**：91.7% 的範本建立於 2025 至 2026 年（見 [`node-frequency.md`](node-frequency.md)）。年份趨勢（§8）受此影響，且 2020 至 2024 各年的樣本小。
7. 這些數字描述的是公開範本，不代表一般內部 workflow。

## 5. 用途分類（主類別）

每個節點取一個主類別。判斷順序是「越專用越優先」：先看是否有跨執行狀態、環境變數，再看有專用原生節點的工作（雜湊、XML、檔案、HTTP、Markdown、HTML、去重、排序、彙總、合併、展開、切片、過濾、日期等），最後才是泛用的字串、JSON、欄位對應與條件判斷；程式碼很複雜（分支、迴圈、函式多，或行數長且有分支）者一律歸為「自訂演算法與複雜商業邏輯」。規則全文另存於機器可讀的規則檔（未納入本 repo）。分母 27,074。

| 主類別 | 節點數 | 占比 | 行數中位數 | 對應原生節點 | 可取代程度 |
|---|---|---|---|---|---|

## 6. 可由原生節點取代的估計

這是**啟發式估計，會有誤判**（見 §2、§7）。四個口徑由嚴到寬，分母都是 27,074：

| 口徑 | 定義 | 節點數 | 占比 |
|---|---|---|---|
| **嚴格估計** | 主類別屬「可取代」類別，且程式碼 ≤ 15 行，且沒有跨執行狀態、環境變數、也不是自訂演算法 | 9,449 | **34.9%** |
| **中間估計** | 主類別屬「可取代」或「部分可取代」類別（不限行數），且沒有跨執行狀態、環境變數、也不是自訂演算法 | 15,586 | **57.6%** |
| 寬鬆上界 | 任何位置命中任一可取代類別的樣式 | 26,529 | 98.0% |
| （參考）命中專用原生節點樣式 | 任何位置命中有專用原生節點的類別（不含泛用的欄位對應、條件、字串、JSON） | 11,542 | 42.6% |

**建議的讀法**：「約 35% 至 58%」。嚴格估計偏保守，中間估計把較長但仍屬資料整形的節點也算進來。寬鬆上界幾乎等於 100%，因為幾乎每個節點都至少碰到欄位對應或條件判斷，所以它沒有資訊量，只當作邊界。

不可取代的部分：自訂演算法與複雜商業邏輯 38.5%，跨執行狀態 3.6%（兩者互不重疊，因為歸類時跨執行狀態優先）。

**嚴格估計的組成**（前 8 類）：

| 主類別 | 節點數 | 占全部（÷27,074） | 占嚴格估計（÷9,449） |
|---|---|---|---|
| 欄位對應、改名與組裝（含簡單條件） | 5,882 | 21.7% | 62.2% |
| JSON 解析／序列化 | 517 | 1.9% | 5.5% |
| 字串處理與正規表達式 | 483 | 1.8% | 5.1% |
| 檔案與二進位資料處理 | 450 | 1.7% | 4.8% |
| 去重 | 311 | 1.1% | 3.3% |
| 日期時間處理 | 280 | 1.0% | 3.0% |
| 陣列展開成多個項目 | 270 | 1.0% | 2.9% |
| 依條件過濾項目 | 233 | 0.9% | 2.5% |

**對閘門設定的敏感度**：自訂與否的判斷靠複雜度閘門。把閘門放寬或收緊，數字如下（同一批節點）：

| 閘門設定 | 嚴格估計 | 中間估計 | 歸為自訂 |
|---|---|---|---|
| 最終（本文使用） | 34.9% | 57.6% | 38.5% |
| 寬鬆（只擋 > 40 行或複雜度 ≥ 18） | 35.1% | 73.1% | 22.8% |
| 嚴苛（> 20 行且複雜度 ≥ 3 即視為自訂） | 32.6% | 48.5% | 47.7% |

嚴格估計對閘門不敏感（32.6% 至 35.1%）；中間估計對閘門很敏感（48.5% 至 73.1%），因為 16 至 40 行的節點最難判斷。

**範本層級**：在 7,678 個至少有一個「有程式碼文字的 Code 節點」的範本中，**所有**這類節點都符合嚴格估計的範本有 1,378 個（17.9%）；符合中間估計的有 2,962 個（38.6%）。也就是說，照這個估計，約 18% 至 39% 的含 Code 範本可以完全不用 Code 節點。

## 7. 抽樣校驗

為了知道啟發式分類有多可靠，由人工從結果中隨機抽樣、讀程式碼判斷。只回報數字與誤判類型。

| 輪次 | 抽樣 | 結果 |
|---|---|---|
| 第一輪（調整前） | 100 個被分到「可取代」類別的節點 | 主類別與可取代判斷都合理 52；主類別不貼切但「可取代」判斷合理 34；「可取代」判斷不合理 14。**可取代判斷合理 86%**，主類別吻合 52% |
| 第一輪（調整前） | 100 個被分到「自訂演算法」的節點 | 確實屬自訂或複雜邏輯 86；其實可用原生節點或運算式 14。**合理 86%** |
| 第二輪（調整後，全新抽樣） | 100 個「可取代」 | 主類別與判斷都合理 65；主類別不貼切但判斷合理 30；判斷不合理 5。**可取代判斷合理 95%**，主類別吻合 65% |
| 第二輪（調整後，全新抽樣） | 100 個「自訂演算法」 | 合理 84；不合理 16。**合理 84%** |

第二輪兩項合計 179 / 200（89.5%）。本文所有數字都是用調整後的規則算的。

**主要誤判類型**（第一輪，據以調整規則）：

- 關鍵字誤中：資料裡的字（例如節點或欄位名稱含「duplicate」「seen」）被當成去重；`Math.random` 或 `uuid` 的子字串誤判成產生隨機值；只是提到 `mimeType`、`fileName` 就被當成檔案處理。
- 複雜度估計偏低：兩層迴圈、跨多個上游節點的巢狀比對、手寫狀態機，在 40 行以內被當成可取代。
- 泛用類別互相搶位：欄位對應、條件、日期、字串在同一個節點裡常同時出現，主類別選哪個本來就接近隨意。
- 自訂誤判：很長但只是在組 HTML 或訊息文字、或只是一大串常數的節點，被複雜度閘門歸成自訂。

**第一輪後做的調整**：拿掉只靠關鍵字的樣式；日期、字串、條件類改成要累積足夠次數才算命中；「合併」要求同時引用兩個不同的上游節點；複雜度不再把 `||`、`??`、箭頭函式算進去（它們在欄位對應裡太常見），改為重新校準行數與分支的閘門；欄位對應需有實際組裝物件的證據才能當主類別；很短又沒命中任何樣式的節點歸為欄位對應。閘門的數值是用第一輪的 200 個已標記節點微調的，所以第二輪改用全新抽樣來檢查。

**第二輪仍存在的誤判類型**：長度 16 至 40 行、有一些分支的資料整形節點（是否「可取代」本來就見仁見智）；用 `this.helpers.getBinaryDataBuffer` 之類的二進位操作，原生節點不一定有對應選項；Python 寫的簡單 HMAC 簽章被複雜度閘門歸成自訂（該類本可用 Crypto 節點）。

**限制**：校驗者只有一人，只看每個節點的開頭片段，標準偏主觀。樣本各 100 個，單看抽樣誤差約 ±6 至 ±7 個百分點。

## 8. 依建立年份的趨勢

年份是範本在 n8n.io 的建立時間，不是節點版本。含舊版 `Function`／`Function Item` 節點的範本在全部樣本只有 355 個（2.5%），多在早期，不影響下表的判讀。2019 年及以前有 24 個範本，沒有 Code 節點，未列入表中。

| 年份 | 範本數 | 含 Code 的範本占比 | Code 節點數 | Code 占非便條節點 | Code 為主的範本占比 | 嚴格估計占比（分母：有程式碼的 Code 節點數） |
|---|---|---|---|---|---|---|
| 2020 | 307 | 0.7% | 3 | 0.3% | 0.3% | 66.7% (3) |
| 2021 | 136 | 0.7% | 1 | 0.1% | 0.0% | 0.0% (1) |
| 2022 | 143 | 4.9% | 15 | 1.4% | 0.7% | 26.7% (15) |
| 2023 | 86 | 46.5% | 63 | 8.1% | 9.3% | 47.6% (63) |
| 2024 | 462 | 33.5% | 275 | 4.6% | 0.6% | 53.6% (265) |
| 2025 | 6,564 | 51.4% | 8,707 | 8.6% | 1.8% | 37.4% (7,002) |
| 2026 | 6,225 | 77.8% | 20,818 | 17.6% | 3.9% | 33.7% (19,725) |

**觀察**：

- 新範本沒有改善的跡象。2025 年含 Code 的範本占 51.4%，2026 年升到 77.8%；Code 占非便條節點的比例由 8.6% 升到 17.6%。
- 2026 年的範本只有 6,225 個，卻貢獻了 20,818 個 Code 節點，占全部 Code 節點的 69.7%。
- 嚴格估計占比由 2024 年的 53.6%（只有 265 個節點，樣本小）降到 2025 年的 37.4%、2026 年的 33.7%。
- 2020 至 2023 年的 Code 節點很少（各年 ≤ 63 個），比例不穩定，不宜解讀。
- 這裡只描述數字，不推測原因。

## 12. 正當使用 Code 的情境

官方 Skill 的立場是「門檻高，但不是絕對不要」。以下情境用 Code 是合理的（細節見 [`../spec/native-first.md`](../spec/native-first.md) §4）：

1. **跨多個來源、對整批資料一次計算**：同時讀好幾個上游節點、建立查找表或累加器，再套用到第三份資料；硬寫成運算式會變成難以除錯的超長一行。
2. **有狀態、多步驟中間結構**：單筆工具（運算式、Edit Fields）碰不到的建構，例如狀態機、依序消耗的額度。
3. **沒有原生對應的自訂邏輯**：評分與排名演算法、文字相似度、依資料形狀逐筆分支、由迴圈組出的巢狀物件、帶多種格式容錯的 AI 輸出解析器。
4. **原生節點沒有暴露的細節**：非標準簽章、需要防時序攻擊的比對。
5. **需要外部函式庫**，而且確認不是 Crypto 節點或 Luxon 運算式就能做。

本文的資料與此相符：被歸為自訂演算法與複雜商業邏輯的節點中位數 47 行，明顯長於整體的 21 行；另有 3.6% 的節點用到跨執行狀態（`$getWorkflowStaticData`），這類目前沒有一對一的原生節點，只有「只處理新資料」這個用途可以改用 Remove Duplicates 的跨執行模式或 Data Table。

## 13. 如何使用

產生或修改 workflow 時：

1. **先走決策順序**：運算式 → Edit Fields 的箭頭函式 → 原生節點（§11 對照表）→ 最後才是 Code。官方的快速自測：能不能把這段工作描述成「拿這一筆資料，然後……」？如果可以，就是用錯工具。
2. **對照本文的類別找原生節點**：去重、排序、彙總、展開、過濾、切片、日期、雜湊、XML、HTML、Markdown、檔案、HTTP、等待，都有專用節點。這些在社群範本的 Code 節點裡合計約占 16.4%（主類別）。
3. **用了 Code 就在節點 `notes` 寫為什麼不能用原生節點**，一到三句，點出評估過哪個原生節點、為什麼不行（格式見 [`../spec/native-first.md`](../spec/native-first.md) §5；節點 notes 的一般規則見 [`../spec/references-disclosure.md`](../spec/references-disclosure.md) §7）。寫不出具體理由，就改用原生節點。
4. **收尾時揭露 Code 節點數量**：依 [`../spec/native-first.md`](../spec/native-first.md) §7，在 Layer 3 便條的建議事項寫 `native-first:code-node`，例如「已採用（Code 節點：N 個／全部節點 M 個）」，並逐條列出理由；沒有用就寫「未使用 Code 節點」。
5. **不要矯枉過正**：把十行清楚的程式拆成十個節點未必更好懂；取捨寫進 `notes`。

本文的比例只用來說明「社群範本的樣子」，不是產生時的判斷標準，也不是門檻。判斷標準是上面的決策順序與理由。
